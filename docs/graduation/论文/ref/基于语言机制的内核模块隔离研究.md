基于语言机制的内核模块隔离研究

摘要：操作系统内核是计算机系统的核心，其安全性对系统的稳定运行至关重要。由 于历史遗留的限制，Linux 等通用操作系统在架构设计中缺乏对安全性的考虑，许多 内核模块因出现内存安全问题而导致系统崩溃，同时，复杂的模块间依赖关系使得模 块的热更新难以实现。近年来，许多工作通过特定的硬件扩展或者基于软件方法来实 施内核模块的隔离，从而缓解内存安全问题对内核的影响，然而，这些方案因性能开 销或灵活性不足难以适用于内核模块。随着编程语言的演进，诸如 Rust 等兼具高性 能和内存安全的现代语言为实现高效、轻量化且细粒度的隔离提供了新思路。
本文提出了 MOA T，一个通用、灵活、低开销的的内核模块隔离框架，通过Rust 语言提供的的类型与内存安全，实现语言驱动的内核模块隔离与热升级，这些具有隔 离属性的模块称为隔离域。MOA T有几个关键的新颖之处，首先，基于系统分解和模 块化思想，MOA T将隔离所需的基础设施与隔离域的实现解耦， 将系统划分为可信计 算基（TCB）和域集合两部分， 这使得MOA T可以轻松移植到不同的操作系统中。
针 对以往基于语言的隔离研究， Moat 进一步细化了安全代码和不安全代码的边界，并 将 TCB 划分为域管理运行时和域基础库。通过在域基础库中对低级内核资源的所有 不安全操作进行安全封装，所有的域集合可以完全使用安全的代码实现。其次，为了 实现完整的内存隔离和故障隔离， Moat 设计了一套用于隔离域之间以及隔离域与原 生内核模块之间通信的通信机制。
最后，MOA T利用状态数据的分离存储实现隔离域 的热升级， 基于读-复制-更新 （Read-Copy-Update） 和优化的读写锁机制， 为有状态和 无状态隔离域设计了热更新策略，以最大限度地缩短更新时的停机时间。
为了评估所提出的设计，本文构建了一个名为 AlienOS 的 Rust 内核，其由 29 个 隔离域构成， 并基于MOA T对 Linux 内核进行了安全重构。
实验结果表明，MOA T的 跨域调用速度比对比方案快三倍，而吞吐量开销仅为 1% 至 2%。此外，所提出的实 时更新策略比对比方案实现了更短的服务暂停时间。
关键词：操作系统；内核模块隔离；热升级；内存安全；编程语言

Research on Kernel Module Isolation Based on Language Mechanism 

Abstract: The operating system kernel is the core of a computer system, and its security is critical to the stable operation of the entire system. Due to historical constraints, general- purpose operating systems such as Linux were not originally designed with strong security considerations. As a result, many kernel modules can crash the system when memory safety violations occur. Moreover, the complex dependency relationships among modules make live updates difficult to implement. In recent years, numerous studies have attempted to iso- late kernel modules through hardware extensions or software-based techniques to mitigate the impact of memory safety vulnerabilities on the kernel. However, these approaches are often unsuitable for kernel modules due to either performance overhead or insufficient flexi- bility. With the evolution of programming languages, modern languages such as Rust, which combine high performance with memory safety, provide new opportunities for achieving ef- ficient, lightweight, and fine-grained isolation. This paper presents MOA T, a general-purpose, flexible, and low-overhead kernel mod- ule isolation framework. Leveraging Rust ’s type and memory safety guarantees, MOA T enables language-driven kernel module isolation and live updates. Modules with isolation properties are referred to as isolation domains. MOA T introduces several key innovations. First, following the principles of system decomposition and modularization, MOA T decou- ples the infrastructure required for isolation from the implementation of isolation domains. The system is divided into two parts: a Trusted Computing Base (TCB), also referred to as the isolation infrastructure, and a set of domains. This design allows MOA T to be easily ported to different operating systems. Building on prior research on language-based isolation, MOA T further refines the boundary between safe and unsafe code by partitioning the TCB into a do- main management runtime and a domain base library. By providing safe abstractions for all low-level kernel resource operations within the domain base library, all domains can be imple- mented entirely in safe Rust. Second, to achieve comprehensive memory isolation and fault isolation, MOA T designs a communication mechanism that supports interactions both among isolation domains and between isolation domains and native kernel modules. Finally, MOA T

enables live updates of isolation domains through separated storage of state data. Based on Read-Copy-Update (RCU) and an optimized read –write lock mechanism, MOA T provides live update strategies for both stateful and stateless isolation domains, thereby minimizing service downtime during updates. To evaluate the proposed design, we built a Rust-based kernel named AlienOS, con- sisting of 29 isolation domains, and also performed a secure refactoring of the Linux kernel based on MOA T. Experimental results show that MOA T achieves cross-domain invocation performance three times faster than the comparison approach, while incurring only 1% –2% throughput overhead. Furthermore, the proposed live update strategy achieves significantly shorter service pause times compared with existing approaches. Key Words: Operating system; kernel module isolation; live updates; memory safety; pro- gramming languages

1 绪论

1.1 研究的背景和意义

 现代操作系统内核作为计算机系统的核心，承担着管理硬件资源、调度任务和提 供基础服务的关键职责。传统单体内核设计通过共享地址空间实现模块间高效协作， 却以牺牲安全边界为代价。
以Linux 为例， 其庞大的代码库（截至2022 年，5.11 版本 已包含约 3000 万行 C 代码[1]） 中， 约60% 为设备驱动模块， 而内存安全问题 （如缓冲 区溢出、释放后使用）占据了内核漏洞的绝大多数比例。研究统计表明，驱动模块贡 献了绝大多数的内核安全缺陷 [2-5]，这些缺陷往往通过复杂的模块依赖链蔓延，引发 系统故障。
例如，2021 年 Linux 内核的 TIPC 协议栈堆溢出漏洞（CVE-2021-43267[6]） 导致远程攻击者可触发系统崩溃，凸显了模块隔离机制的迫切需求。
内存隔离是模块隔离的关键属性，其目标在于通过硬件或软件手段，防止一个执 行单元的错误或恶意行为影响其他单元的内存数据，从而提升系统的安全性和隐私 性[7-8]。
同时， 内核模块仍然需要高性能的跨模块通信以保证内核的效率。
因此， 新的 隔离方法必须支持低开销的内存隔离。
故障隔离对提高内存隔离的有效性有很大的作 用[9-10]。当内核模块在运行时因为违反内存隔离属性或其他原因而出现错误时，模块 有责任将错误限制在内部而不蔓延到其它模块中， 并且模块需要把发生错误期间分配 的资源释放，以避免可能发生的资源泄露和死锁问题。
对内核模块实施热更新是一项富有挑战的任务。
支持热更新允许对运行良好的模 块进行升级以增加额外的功能， 或者对发生过故障的模块进行替换以修复已存在的错 误。已有的热更新方法要不只能工作在较小的补丁上[11-14]，要不就是针对特定的内核 模块[15-19]， 缺乏一种有效的机制为不同的模块实现统一的热更新方法。尽管实现模块 的隔离并不需要关注热更新，但反过来，实现模块的热更新在一定程度上蕴含了隔离 属性，然而，许多工作没有意识到隔离属性和热更新之间的关联性。
操作系统内核模块隔离是一个重要的议题，早在几十年前就被提出 [20-21]。然而， 由于历史传承、性能成本考量等因素， Unix、Linux 等主流现代操作系统内核仍然基 于 C 语言的宏内核形式，在现有架构下难以解决类型和内存安全问题。到目前为止， 相关研究已经有很多成果， 例如硬件解决方案[7-8,22-32] 和软件解决方案[33-42]， 但都存在 诸如系统开销等问题难以解决。此外，基于安全语言的隔离相关工作也有一些[9,43-47]，

但存在较强的限制，这些传统的安全语言需要运行时以进行垃圾回收，尽管垃圾回 收算法已经进行了高度优化，但对于具有微秒级延迟的现代高速存储设备来说，开 销依然很高 (在高速网卡设备的典型工作负载下 [48], 最快的垃圾收集语言比 C 语言慢 20-50%)。
近年来，随着 Rust 语言的兴起及其内存安全性、无需依赖垃圾回收的零成本抽 象能力等特性，为系统编程领域注入了新的可能性。Rust 语言分为两部分：safe Rust 和 unsafe Rust。safe Rust 指的是所有在语言严格的静态检查（所有权、借用规则、生 命周期[49]） 下都能被证明是安全的操作， 编译器会无条件地确保这些操作不会导致内 存错误或未定义行为。unsafe Rust 通过 unsafe 关键字显式地定义了物理边界，允许 开发者执行编译器无法验证的底层操作（例如原始指针解引用、内存布局控制或外部 函数调用） 。尽管safe Rust 具有诸多优势，但对于操作系统开发而言，unsafe Rust 仍 然必不可少，因为 Rust 编译器无法静态保证对各种底层系统资源的操作安全性。因 此，为了能够用 safe Rust 编写更多功能，并充分利用编译器的安全检查——从而减 少因误用不安全型代码而导致的漏洞和未定义行为[50-51]，一种有效的策略是将 unsafe Rust 代码限制在最小的作用域内，并用精心设计的安全抽象对其进行封装。
通过编译时所有权检查与借用规则，Rust 无需垃圾回收即可杜绝数据竞争、 悬垂 指针等内存错误， 这一特性与内核模块隔离的需求高度契合。Redleaf[45]、Asterinas[47]、 Theseus[44]等研究工作开始关注基于 Rust 语言的内核隔离方法或者基于语言机制实现 模块的热更新。尽管这些工作探索了 Rust 在提升内核模块安全性和提供更丰富功能 方面的潜力。
然而， 它们都使用Rust 构建了自己的新操作系统， 以完全替换现有的商 业操作系统内核，这使得这些解决方案难以应用于现有工作。
总而言之，现有的解决方案无法在内核模块隔离、模块的热更新以及通用性上找 到一个平衡，因此，实现一个（1） ：支持模块的高效、灵活和细粒度的内存隔离（低 开销） ； （2） ：支持模块内的故障隔离（高可靠性） ； （3） ：支持对隔离模块进行组件级 别的热更新（热更新） ； （4） ：隔离和热升级适用于不同的模块，可以应用在不同的操 作系统系统中（通用性）的内核模块隔离框架是一个非常值得探索的研究领域。

1.2 本文的研究内容

 针对基于 Rust 语言的内核隔离相关工作存在的性能和通用性问题， 本文在Redleaf、 Theseus 的工作思路的基础上，提出了一种新的内核模块隔离框架 Moat，基于系统分

解和模块化思想将隔离所需的基础设施与隔离模块的实现进行了解耦， 并将safe 代码 和 unsafe 代码的边界进行了提炼，抽取出一个 TCB 作为隔离的基础设施布置在内核 中， 其他内核模块可以根据接口基于TCB 实现基于 safe rust 的隔离。
其中，TCB 对内 核中针对关键资源的 unsafe 代码进行了安全性封装， 设置域运行时模块和域基础库模 块。运行时模块负责系统初始化并在系统运行中管理所有的隔离域 (注册、卸载、热 更新)，域基础库模块负责提供安全隔离域实现所需的内核资源安全抽象和用于堆隔 离和热更新的各类堆分配器。通过仔细划分系统无关部分和系统相关部分，进而实现 对商用宏内核操作系统的良好适配性。归功于良好的模块隔离，本文进一步实现了内 核模块的热更新，并针对无状态或有状态的不同特征的内核模块，引入了优化的任务 检测方法以减少热更新所需时间。
为了评估所提出的解决方案， 本文构建了一个名为AlienOS 的 Rust 内核， 其由29 个隔离域构成，并基于 MOA T对 Linux 内核进行了安全重构。实验结果表明，MOA T 的跨域调用速度比对比方案快三倍，而吞吐量开销仅为 1% 至 2%。此外，所提出的 实时更新策略比对比方案实现了更短的服务暂停时间。
本文的主要贡献如下：
1. 本文提出了一种新的隔离架构，用于逐步升级现有商业操作系统内核（例如 Linux）的安全性。所提出的隔离域所需的基础设施与域的实现解耦，并且精心 设计了一组接口和安全抽象。
2. 在模块隔离域之上，本文为这些域设计了一种实时更新策略，该策略适用于有 状态和无状态模块。
Moat 使用 RCU 机制来提高无状态域的更新效率，并基于 优化的读写锁方法设计有状态域的实时更新。
3. 基于所提出的隔离抽象模型，本文实现了一个完全符合模块化隔离设计的小型 操作系统原型。
本文在Linux 上进一步进行了初步的隔离转换， 实现了Linux 三 个内核模块的隔离。

2.1 基于硬件机制的隔离

由于历史性能优先策略导致这些系统中广泛使用不安全的 C/C++ 代码，进一步加剧 了风险。解决内存安全问题的直接方案是实施隔离机制。从功能层面看，隔离主要包 含两个核心维度：内存隔离（Memory Isolation） ：作为基础机制，确保不同执行单元 （如进程、 内核模块或子系统） 间的内存访问互不干扰； 故障隔离 （Fault Isolation） ： 将

尽管硬件级内存隔离机制（如虚拟内存与特权分级）为用户空间程序提供了基 础保护，但用于地址空间隔离的进程抽象会引入过高开销。新兴技术如内存标记 （MPK[62]）与指针认证（ ARM MTE [63], ARM PAC [64]）能实现更细粒度的进程内隔 离。这些技术探索了以内存标签和功能为中心的细粒度隔离的想法 , 内存保护密钥 （MPK 2.1）是 Intel 在 SkyLake CPU 中引入的一种新的隔离机制。MPK 允许通过使用 4 位保护密钥（保存在页表条目的未使用位中）标记各个页面，在单个地址空间内强 制实施隔离。

2.2 基于软件方法的隔离

 尽管现代内核采用地址空间布局随机化 [68]、栈溢出保护 [69]等众多工具检测和缓 解常见内存安全漏洞，但这些机制均不是面向内核模块设计的。
基于软件的隔离机制[10,33-39]通过在操作系统中建立逻辑约束实现模块分离。经典

方案软件故障隔离（Software Fault Isolation, SFI ）通过插入边界检查指令限制内存访 问与代码执行，强制建立安全边界，阻止不可信代码访问未授权内存区域或执行恶意 操作。SFI 的核心机制是对内存地址和控制流的动态检查，通过屏蔽地址或限制跳转 目标，将代码的行为限制在预定义的合法范围内，同时通过静态验证器在加载代码时 确保其符合安全策略。虽然 SFI 在支持多语言隔离、降低隔离开销与跨模块通信成本 之间实现了有效平衡[70-71]， 但其硬件无关的实现方案仍存在显著性能损耗[25]。
这些局 限源于两个根本性约束： • 语义盲区：SFI 依赖编译器插件生成安全检查， 但编译器缺乏对程序逻辑的语义 理解，只能机械地为所有潜在代码路径插入检查指令，从而导致性能下降； • 人工依赖：需要开发者手动指定待保护模块与函数。
微内核架构也是一种软件隔离方法。
微内核架构[40-42]通过将操作系统的核心功能 极度精简，仅保留进程管理、内存管理和进程间通信（ IPC）等基本功能，其余诸如 文件系统、驱动程序、网络协议栈等服务被移至用户态运行，从根本上改变了传统单 体内核的设计。这样的设计实现了明确的模块边界，每个服务运行在独立的地址空间 中，通过受控的 IPC 进行通信，这种强隔离不仅提高了系统的安全性，也增强了模块 的可靠性——一个服务的崩溃通常不会直接导致整个系统的瘫痪。典型的微内核操作 系统如 seL4[40]和 MINIX 3[41]展示了高安全性和可靠性的设计理念，这些系统在航空、 医疗等安全关键领域得到了广泛应用。然而，微内核的隔离机制也引入了一些缺点。
由于服务之间的频繁通信需要通过用户态和内核态的多次上下文切换，通信开销较 高，导致性能上的损失。除此之外，子系统交互方式的彻底改变导致现有的大量内核 组件无法被复用，而在用户态提供这些组件所依赖的运行环境需要大量的工程工作， 还面临内核子系统接口变化的问题。与微内核类似的技术还有用户态用户驱动，比如 DPDK[72]、Fuse[73]等。

2.3 基于传统安全语言的隔离

 操作系统模块隔离与热更新的研究持续演进。随着编程语言的进步，系统级语言 （如 C#、Go 和 Rust）将高性能与内存安全相结合，正从基础层面解决内存安全问题。
根据谷歌报告显示，随着开发转向内存安全语言， Android 系统中内存安全漏洞占比 在六年内从 76% 降至 24%[74]。这些语言为构建高效、轻量级且细粒度的隔离机制开

辟了新路径——现代编程语言的类型系统与安全保障，可在不损失性能的前提下实现 上述目标。
大多数安全语言依赖垃圾回收机制 (如 C#[75]和 Go[76])，相比利用所有权 [77]和线 性类型系统[78]实现类型和内存安全的 Rust[79]语言，它们无需手动分配/释放内存，也 不需要关注所有权和生命周期等复杂的编程概念。尽管优势明显，但基于垃圾回收的 安全语言在实现低开销的隔离方面仍有困难。
V erve[52]提出并实现了操作系统 V erve，这是一种使用类型化汇编语言（TAL）和 自动化定理证明技术验证类型安全和内存安全的操作系统。V erve采用分层结构设计， 其中低层的 Nucleus 负责与硬件和内存的交互，并通过 Hoare[80]逻辑进行正确性验证， 而高层的内核和应用则使用安全的 C# 代码编写，并编译为 TAL 后自动验证其安全 性。通过这种设计，V erve实现了对系统各个组件的静态验证，包括运行时系统、设 备驱动和应用程序的安全性， 从而在操作系统中消除了缓冲区溢出和内存悬挂等常见 低级错误。Biscuit[53]探讨了使用高级语言 Go 编写 Posix 内核的可行性，其开发充分 利用了 Go 语言的类型安全、垃圾回收和并发机制。
V erve[52]和 Biscuit[53]使用基于垃圾回收的语言重新实现操作系统，这些工作证明 了现代高级语言可以从底层设计上降低操作系统内核发生的错误并在高层简化对操 作系统的形式化验证工作，然而，由于这些语言通常不提供低级硬件交互的接口，这 导致需要修改其运行时，而且，其垃圾回收器存在不可预测的暂停时间，这些缺陷造 成了无法在商用操作系统中得到支持。

2.4 基于 Rust 语言的隔离

 Rust 是一门相对年轻的系统编程语言，诞生于 Mozilla 研究院，其核心目标是解 决一个长久困扰系统编程领域的难题：如何在不牺牲性能的前提下，实现内存安全和 线程安全？传统上，像 C 和 C++ 这样的语言提供了极高的性能和对硬件的精细控制， 但它们依赖程序员手动管理内存 （如分配和释放） ， 这极易导致诸如空指针解引用、 缓 冲区溢出、数据竞争等严重错误，这些错误往往是安全漏洞和程序崩溃的根源。另一 方面，拥有垃圾回收（GC）机制的语言（如 Java, Go, Python ）虽然大大减轻了内存 管理的负担并提高了安全性，但 GC 带来的运行时开销和不可预测的停顿时间，使得 它们在某些对性能和资源控制有严苛要求的系统编程场景（如操作系统内核、游戏引 擎、嵌入式设备、高性能网络服务）中显得力不从心。
Rust 致力于成为一门安全、并发、高效的语言，同时保持实用性和高性能。它不 依赖垃圾回收， 而是通过一套独特且强大的编译时所有权系统与借用规则来达成其安 全目标。这套机制是 Rust 最核心的创新和标志性特征。
所有权的概念是 Rust 的基石。在 Rust 中，每一个值在任意时刻都有一个明确的 所有者 （通常是一个变量） 。
这个所有权遵循几条关键规则： 首先， 一个值只能有一个 所有者。其次，当所有者（变量）离开其作用域时，它所拥有的值就会被自动、确定 性地清理（释放内存或其他资源） ，这个过程称为“Drop” 。最后，值的所有权可以在 变量之间移动（Move） ，移动发生后，原来的变量将失效，不能再被使用，从而避免 了意外的“双重释放”或“悬垂指针” 。这种移动语义默认发生，确保了资源的唯一 归属。这与许多语言默认进行浅拷贝（可能留下悬垂指针）或深拷贝（可能带来性能 开销）不同。当确实需要复制堆上的数据时，Rust 要求显式调用克隆（Clone）方法。
然而，如果只有所有权和移动，编写复杂程序会非常受限，因为频繁地移交所有 权会导致代码难以组织。
因此，Rust 引入了借用的概念。
借用允许你临时引用一个值， 而不需要获取其所有权。引用分为两种：不可变引用和可变引用。不可变引用允许你 读取数据但不能修改它，并且可以同时存在多个不可变引用指向同一个数据。可变引 用则允许你修改数据， 但有一个极其严格的限制： 在同一个作用域内， 对同一块数据， 要么只能存在一个可变引用，要么只能存在多个不可变引用，二者绝对不可共存。这 个规则由编译器在编译时严格检查，被称为借用检查器。
为了实现内存安全和零成本抽象，Rust 引入了生命周期的概念。
生命周期是Rust 编译器用来跟踪引用有效作用范围的一种标注。
它确保引用在整个使用期间都指向有 效的内存。虽然编译器通常能自动推断生命周期，但在某些复杂场景（尤其是函数签 名或结构体定义中涉及引用时） ，需要开发者显式标注生命周期参数，以向编译器提 供必要的信息。
为克服传统安全语言的局限，部分研究转向采用安全语言 Rust——其性能与 C 语言相当——来开发兼具高性能与强安全保障的新系统。Redox[81]、RustyHermit[82]及 Drone[83]等项目虽在不同架构上实现了 Rust 内核，但仅将其作为更安全的 C 替代品。
TockOS[54]与 Asterinas[47]则更进一步：通过将内核划分为不安全世界与安全世界，其 中小型不安全世界可利用 Rust 的 unsafe 特性执行面向硬件的底层操作，并向安全世 界暴露安全抽象接口；而安全世界完全采用 safe Rust 编写，从而保留 Rust 的安全保 障。
鉴于 Rust 的安全与性能优势，主流操作系统已开始将其集成至内核：Linux[84]与 Windows[85]正逐步引入 Rust 代码，旨在利用其类型安全与内存安全特性减少内核缺 陷并提升系统稳定性。这些系统通过混合 Rust 与现有 C/C++ 代码库，实现了向更安 全编程实践的渐进式迁移。然而，此类系统尚未探索 Rust 在类型与内存安全之外的 深层能力，如模块隔离与热更新机制。
图 2.3 Redleaf 的隔离设计 Redleaf[45]是一个使用 Rust 开发的微内核，旨在探索语言安全性对操作系统组织 结构的影响，尤其是在实现细粒度隔离方面的潜力。不同于依赖硬件地址空间的传统 操作系统，RedLeaf 利用 Rust 的类型和内存安全特性实现隔离。这种设计避免了昂贵 的硬件隔离机制，使得轻量级隔离成为可能，并且降低了性能开销。
RedLeaf 的核心 抽象是语言支持的隔离域（ language-supported isolation domain ） ，这些域作为独立的 隔离单元，可动态加载和安全卸载，并且崩溃时不会影响其他域的执行。与之前利用 语言机制实现子系统隔离的系统[9,43,46]类似，RedLeaf 中隔离的实现依赖以下原则： 堆

隔离、 可交换类型、 所有权追踪、 接口验证和跨域调用代理。
尽管redleaf 在使用 Rust 实现高效、细粒度的隔离子系统上已经迈出了一大步，这并没有发挥出 Rust 语言的 所有能力。
首先，Redleaf 缺乏对 safe 和 unsafe 边界的划分，与 TockOS[54]和 Asterinas[47]类 似，Redleaf 强制要求隔离域禁止使用 unsafe 代码, 然而其大多数域都依赖于域相关 的可信库， 而可信库中大量的 unsafe 代码破坏了 Rust 语言提供的安全保证， 使得整 个系统中完全由 safe 代码构成的部分比例大大减少。其次， Redleaf 依靠状态检查点 机制来实施故障隔离，然而，仅仅靠检查点状态的保存和恢复无法正确释放由故障导 致的资源泄露的，如果没有将检查点到故障点之间的分配的资源释放掉，即使可以再 次对已经发生故障的域发起请求， 域仍然处于一个不正确的状态。
最后，Redleaf 没有 意识到，对子系统的隔离可以带来更多的扩展功能，比如实现子系统的热升级。
为了应对现有的基于 Rust 的操作系统开发中不正确的 unsafe Rust 使用，Asterinas 提出了一种新的操作系统架构，称为 framekernel，它实现了 Rust 实现内核内部特权 分离的全部潜力，确保了 TCB 的最小化和可靠性。在 framekernel 架构中，整个操作 系统驻留在一个单一的地址空间中，并在 Rust 中实现。内核在逻辑上分为两个部分: 特权操作系统框架 (类似于微内核) 和非特权操作系统服务。只有特权框架才允许使 用不安全，而去特权的服务必须完全用安全的 Rust 编写。作为 TCB，特权框架将所 有低级的、面向硬件的不安全操作封装在安全 api 后面, 被剥夺特权的操作系统服务 使用这些 API 实现各种操作系统功能。Asterinas 在对 Rust 的 safe 和 unsafe 边界划分 上向前迈进了一大步，提出了许多值得借鉴的设计思路。
上述这些工作探索了现代安全语言在提高内核安全性上的潜力，进而提供更丰 富的功能，比如内核模块隔离、安全内核扩展等。然而，它们目前依然存在通用性 的关键问题尚未解决，即都是利用 Rust 语言重新打造了各自的全新操作系统。其中， Redleaf, 没有考虑其隔离方案在主流宏内核操作系统上的适配，导致适用性受到影响; 而 Asterinas 则是为 Linux 应用提供匹配的系统调用。

2.5 热更新

 热更新是一种在无需重启系统的情况下对内核模块进行更新的技术， 分为功能级 别[11-14]和组件级别[15-19] 两种主要方案。kpatch[11]、livepatch[12]等功能级别的热更新允 许开发者通过补丁形式直接修改或替换内核中的特定函数，完成漏洞修复或功能增

强，而无需重新启动系统。功能级别的优点在于其实现相对简单，只需将变更限定在 特定的功能模块内。然而，其局限性也非常明显，即只能在变更对系统整体结构影响 较小的情况下使用，对于涉及接口修改或跨模块依赖的大型更新，功能级别的热更新 显得力不从心。相比之下，组件级别的热更新旨在对整个模块进行全面替换 , 通过保 存旧版本的运行状态，并在新模块加载后迁移状态来实现无缝切换。组件级别的热更 新的 3 个难点在于（1） ：维护组件的状态，在更新后，组件以更新前的状态继续服 务； （2） ：尽可能降低服务暂停时间，这会显著影响那些延迟敏感型应用[86-87] （3） ： 适用于不同的模块。
操作系统模块之间复杂的关系和内部复杂的状态导致已有的支持 组件级热更新的方案往往不能兼顾这 3 点。比如，PlugSched[15]支持对调度器模块进 行热更新并具有较短的服务暂停时间，却无法直接迁移至其他模块。
图 2.4 Theseus 的热更新设计 Theseus[44]是另一个从零开始使用 Rust 编写的实验性操作系统，它重新思考了操 作系统的结构和状态管理问题。
其聚焦于解决现代操作系统中普遍存在的状态泄漏问 题， 这种问题导致模块间的强耦合， 严重阻碍了系统的演进、 容错性和灵活性。Theseus 的设计核心在于通过明确划分操作系统模块边界、 最大化利用语言特性以及消除模块 间状态泄漏，构建一个可以动态演进和高效容错的系统。
Theseus 中的每个模块被称 为“cell” ，它们是运行时独立且可动态加载或替换的单元。这种设计确保了系统在运 行时的灵活性，支持模块的实时热插拔和无中断更新。Theseus 通过 Rust 的内存安全

和类型安全特性，将许多传统由操作系统负责的任务（如内存管理和资源回收）转移 到编译器层面。
这种“内在化设计” （Intralingual Design） 减少了操作系统本身需要维 护的状态量， 简化了状态管理。
特别是，Theseus 实现了无状态的模块交互， 使得模块 更新或恢复时无需担心状态一致性问题。此外，通过模块化的设计理念， Theseus 使 得故障模块可以被独立隔离并恢复，从而提升了系统的容错性。
不幸的是，由于一贯的特权级分离设计，现代商用操作系统内核子系统中保存 了大量用户任务的状态，各个子系统之间依靠复杂的状态数据进行交互，为了实现 Theseus 提倡的无状态设计方法，商用操作系统内核需要进行彻底的推翻和重构，这 在当前显然还不能实现。

2.6 总结和目标

 在这些工作的启示的基础上， Moat 旨在实现一个通用的内核模块隔离和热更新 框架，以探索安全语言 Rust 对操作系统安全性、可靠性和可扩展性的促进作用。
性能优先 Moat 将性能作为首要考量，明确内核隔离与热更新机制不得损害系统 效率。受 Redleaf[45]启发，Moat 采用基于语言的隔离方案实现模块隔离，从而避免了 硬件方案固有的上下文切换与特权级转换开销，并支持模块间低开销隔离。为了进一 步降低 Redleaf 中隔离模块之间的通信开销，Moat 需要避免引入额外的状态检查点机 制。
通用隔离架构 Moat 的设计并非为了实现隔离目标而设计一个全新的操作系统， 而是将隔离和热更新的基础设施与模块实现解耦，使现有操作系统能够以最小的调 整重复使用核心机制。其与既有内核组件协同运作，例如允许基于 Rust 的隔离域与 传统可加载内核模块（LKMs）并存。开发者可根据安全需求灵活选择隔离域或传统 LKM。此外，Moat 提供工具链支持以简化隔离域的开发、编译与部署流程，从而促 进原有的模块向隔离域逐渐迁移。
划分安全和不安全的边界 由于采用了基于语言的隔离方法，Moat 不可避免地需 要处理 Rust 语言中的不安全子集。在分离实施隔离所需的基础设施和模块实现的基 础上，Moat 需要定义安全代码和不安全代码之间的清晰边界 , 从而解决 Redleaf[45]中 大量的不安全代码对整个系统的影响问题。safe 和 unsafe 的边界划分不仅可以让被隔 离的模块从安全的 Rust 代码中受益， 还可以让不安全的代码保留在较小的范围内， 进 而允许对其进行必要的安全审查, 从而增强可靠性。
热更新支持 为了解决模块状态难以管理的问题，在模块隔离的基础上，Moat 提 供了一个通用的内核模块热更新框架。
该框架提供了必要的数据结构和接口来保存和 恢复模块状态，并在模块更新时自动迁移状态数据，从而实现对各种隔离内核模块的 热更新。与 Theseus[44]不同，Moat 不要求模块是无状态的。此外，与 kpatch[11]（仅限 于函数级更新）和 Plugsched[15]（调度器特定）不同，Moat 提供了一个统一的热更新 方法，适用于任意模块——这需要足够的表达能力和通用性。而为了解决模块热更新 导致的服务暂停问题， Moat 同样借助隔离带来的边界划分，提供高效的升级时机检 测和快速的状态同步机制，以最小化服务停机时间。

2.7 本章小结

 本章系统梳理了内核模块隔离与热更新技术的研究现状。
现有工作主要围绕三大 技术路径展开：基于硬件虚拟化或专用硬件的隔离方案虽能实现强隔离，但存在性能 开销大、扩展性差的问题；基于软件的隔离方法（如软件故障隔离和微内核架构）虽 更具灵活性，却往往引入显著的性能损耗或需彻底重构系统，难以兼容现有生态；基 于安全编程语言的方案（如使用 C#、Go 等语言）虽能提升内存安全，但其运行时垃 圾回收机制难以满足内核开发对性能和实时性的严苛要求。
近年来，随着 Rust 语言在系统编程领域的兴起，基于 Rust 的操作系统研究（如 Redleaf、Theseus、Asterinas）展示了利用其所有权模型和类型系统在实现内存安全、 细粒度隔离乃至无状态热更新方面的巨大潜力。这些工作证实了语言级安全机制可 在不依赖硬件的情况下高效实现内核模块隔离。然而，它们多为从头构建的全新系 统，其隔离与更新机制与特定系统架构紧密耦合，缺乏通用性，导致难以直接应用于 Linux 等现有主流操作系统进行渐进式改进。
此外， 在热更新方面， 现有方案如kpatch 等功能级更新灵活性不足， 而Plugsched 等组件级更新又高度特化， 缺乏通用、 高效且能维护状态一致性的通用方案。Theseus 提出的无状态设计虽理想，但要求推翻现有内核的状态管理模型，实用性受限。
在此研究背景下，本文工作的目标是设计并实现 Moat 这一通用框架。它旨在克 服现有方案的局限，核心目标是利用 Rust 的语言安全特性，在不牺牲性能的前提下， 为现有主流操作系统提供一个兼具高性能、通用性、清晰安全边界的内核模块隔离与 热更新解决方案。Moat 力求在隔离机制与业务逻辑之间实现解耦，使其能灵活适配 不同系统，并支持对已有模块进行渐进式的安全加固与动态更新。

3.1 内核模块隔离的总体设计思路

 为实现 Linux 等商用操作系统中的内核模块隔离， Moat 的核心设计思想是利用 Rust 语言构建可复用的 TCB 子系统，封装不安全操作并为隔离模块提供标准安全接 口。若需对现有模块进行隔离化改造，开发者需根据 TCB 接口使用 safe Rust 重写模 块，改造后的模块可与未修改的内核模块共存。在此框架下，操作系统可通过渐进式 改造实现隔离化，使模块获得 Moat 提供的安全性与热更新能力。图 3.1展示了 Moat

架构，其将内核划分为两大组件： （1）TCB：由域管理运行时模块与域基础库模块 构成，集成所有 unsafe Rust 代码以执行系统必要操作（如资源分配） 。域基础库模块 为底层操作提供安全抽象，运行时模块作为最小化运行时环境提供基础系统服务。二 者共同构成隔离与热更新的基础设施， 使开发者专注于隔离域实现而无需处理底层细 节。内部实现上，这两个子模块均分解为系统相关与系统无关部分。
（2）域集合：由 完全基于 safe Rust 实现的隔离域组成的集合。
通过对系统功能的分解， Moat 将一个具有隔离属性的内核系统划分为隔离域集 合、隔离域基础库和隔离域管理运行时，从而将隔离的机制和策略解耦。隔离域集合 定义了隔离单元-隔离域，并描述了其内部约束与外部特征。域基础库的划分则将系 统中不安全的部分从域中分离出来，从而允许隔离域可以完全由 safe 的 Rust 代码构 成。Moat 将那些对开发者来说非常危险的操作， 封装在一系列安全的类型背后， 并向 域开发者提供安全的接口。为了最小化由不安全代码构成的域基础库 , 域基础库只处 理那些必须的不安全操作，而更高级的抽象则由域开发者实施。
Moat 将对域的管理 和系统的基本初始化功能划分到域管理运行时子模块中。
为了在不同的系统之间适配 Moat，域基础库和域管理运行时子模块都由更小的组件组成。
在域基础库的安全抽象之上，Moat 利用堆隔离的思想来实现模块的内存隔离。
此 外，Moat 支持域的故障隔离， 从而将域内部的故障隔离在单个域内部， 而不导致其它 域出现错误。内存隔离是故障隔离的基础，因为内存隔离确保了发生错误的域无法破 坏其它正常域中的内存。为了实现故障隔离，Moat 利用了 Rust 语言内置的异常处理 机制，在发生故障后，通过执行堆栈展开，所有在故障期间分配的资源得以释放，并 最后向调用者返回错误。故障代理进一步简化了故障隔离的实现，使得开发者可以透 明地使用该功能。
隔离属性在另一个角度上促进了对模块进行热更新。
为了实现一个通用高效的热 更新方案，Moat 引入了两个独特的机制。首先，Moat 将域分类为无状态域和有状态 域，并为有状态域引入了一个自定义堆，用于存储域内部的状态数据，这允许在域更 新前后维护域状态数据的一致性并轻松地迁移。其次，为了降低模块更新对用户程 序的影响，Moat 针对无状态域和有状态域实行不同的状态同步方法。无状态域使用 RCU 机制避免了服务暂停，有状态域使用了优化的动态锁使能方法，配合域的接口 属性，可以高效地进行任务检查和快速热更新。与故障隔离类似，热更新代理的引入 屏蔽了热更新的实现细节，为域开发者提供一个透明的接口对象。

3.2 隔离域集合

 在 Moat 中，绝大多数内核功能以隔离域形式实现为动态管理的内核模块。这些 域支持运行时加载、 卸载或热更新。
作为软件定义的隔离单元， 它们通过Rust 的类型 与内存安全机制（而非硬件方案）实现隔离。每个域通过域接口（ Domain Interface） 对外提供服务，在内部，隔离域依赖域基础库中的安全抽象，域的所有的代码完全由 safe rust 编写。每个域都遵守相同的内存管理方式，其包含三类核心堆： （1）私有堆 （private heap） ：用于隔离域内部内存分配（§3.5.1 ） ； （2）共享堆（shared heap） ：支持 跨域通信（§3.5.1 ）;（3）自定义堆（custom heap） ：存储域的状态数据（§3.6.1 ） 。跨 域通信通过域接口的函数调用实现。
域是被独立编译并被动态加载的，这有点类似于 Linux LKM，但又与 LKM 有明 显的差异。Moat 使用 Rust 的 trait 系统为每一类域定义一个 trait(一组函数的集合) 从 而提供一个接口的抽象，这基于对系统的观察 : 内核中的模块通常以一组函数请求其 它模块服务，并导出一组函数给其它模块服务。每个域需要实现其特定的 trait。在实 现层面上，域被强制从 unsafe 代码中解放出来，因为 Rust 的类型安全和内存安全无 法在 unsafe 代码中得到有效验证， 因此域的依赖项只能包含Rust 的 core 和 alloc 安全 集合以及域基础库中的安全抽象。换句话说， Moat 的隔离域具有在实现时定义明确 的边界，并在运行中持续存在。域对外只暴露明确的接口，内部实现细节对外隐藏， 域之间的交互通过接口调用实现。
私有堆和共享堆的建立是隔离属性的基本要求。对于每一个独立可加载的域来 说，其内部所需的内存分配除了来自栈上的分配之外，还需要一个堆进行支撑，如果 所有的域都共享同一个堆进行分配，当域发生故障时，就无法对域所分配的内存资源 进行快速地回收，尽管可以通过维护内存分配的元数据来识别内存资源的所属关系， 这会带来严重的内存开销并且仍然没有加速其回收过程。相反，为每一个域建立专属 的私有堆，在对域进行更新时，允许直接对旧的域的私有堆进行整体回收。
在满足域内部的内存分配情况下，需要考虑隔离域之间的交互情况。这和域内部 不同功能之间交互不同，一个域内部，可能包含不同的功能模块，而这些模块是直接 使用函数调用来进行交互的，这些函数调用传递的数据都来自己私有的堆栈上，不会 传递到其它域中。
域间的函数调用则有不一样的限制， 由于需要确保域间的内存隔离， 不能在域间调用上传递域的私有数据，因此，为所有域提供一个共享的堆是一个理想

的选择，共享意味着其内存是可以由不同的域进行访问的。
自定义堆有点类似于私有堆，但它们执行不同的任务。自定义堆将域的状态数据 与其它数据的存储区分开来，从而实现域更新的状态一致性维护。因此，域的开发者 在决定支持域的热更新能力时，有责任确保域的状态数据和普通数据被正确区分，并 且状态数据的分配被正确定向到自定义堆上。
图 3.2展示了域的的基本形式，以 Domain A 为例，在其内部功能实现中，它通 过使用 Vec::new() 直接在私有堆上分配堆内存，这和普通的 rust 程序是一样的。在 调用 Domain B 的功能前，A 通过 Dvec::new() 在共享堆上分配了内存，并通过 B 的域接口将数据移动到 B 内部。A 为了保存其自身的状态数据，则通过 Arc<dyn VfsInode,CustomHeap> 定义了数据将会被存储到自定义堆上。代码 8展示了域接口 的定义，可以看到，在需要共享或传递数据时，域的接口中都明确定义了需要使用共 享堆的数据结构。

3.3.1 基础库的基本功能

 域基础库中的安全抽象是建立在对域的分析基础上的：在使用 Rust 进行操作系 统开发时， 针对低级内核资源的一些操作不得不使用unsafe Rust 进行实现， 但是域不 允许使用 unsafe Rust， 同时Rust 语言中的内置类型也不足以表达这些资源。
为此， 在 域基础库中，Moat 将编译器检查的不变量 (无缓冲区溢出，无释放后使用 ) 扩展到对 低级内核资源的操作中，让这些资源被无缝地纳入到 Rust 提供的强大静态类型安全 中，这是通过对低级内核资源和相关联的操作进行安全抽象来实现的。对低级内核资

源的安全抽象通常是与系统相关的， 但是用于实施内存隔离的私有堆和共享堆以及用 于实施热更新的自定义堆等基础设施是与系统无关的，因此， Moat 进而将域基础库 分解为较小的组件，以允许 Moat 应用到新的系统中时重用这些基础设施。
针对域基础库的系统无关部分，Moat 提供通用设计与类型抽象并暴露安全接口。
表 3.1列出了域基础库的主要 API， 包括私有堆、 共享堆、 自定义堆的分配与释放、 状 态数据的存储与检索，以及针对互斥锁、安全指针等内核资源的安全抽象。域基础库 作为模块化组件实现，核心目标有两部分： • 安全与不安全边界：将所有需要 unsafe Rust 的底层操作封装为内存/硬件访问的 安全接口（系统相关） 。
• 堆隔离机制：为隔离域提供私有堆、自定义堆与共享堆（系统无关） 。
CoreFunction::* API 调用域管理运行时的接口访问系统资源。
HeapAllocator 与 SharedHeapAlloc API 分别处理私有堆与共享堆的内存分配。这些 API 开发者不 直接调用，而是使用更高级的数据结构——例如开发者在 safe Rust 代码中执行堆分 配时，其内部自动调用 HeapAllocator；当为跨域通信分配共享堆数据时，则调用 SharedHeapAlloc。开发者通过 storage::insert/get/remove 存储与检索状态数据， 此类数据持久化存储于自定义堆中。
仅使用安全的 Rust 代码无法将所有的内核模块实现为安全的域，比如，一些模 块需要处理内存读写或设备 I/O，这些操作是 Rust 编译器无法验证的，因此不可避免 地需要引入 unsafe 代码来实现这些功能。然而，unsafe 代码是危险的，它不具备 safe Rust 的安全保障，如果不小心处理，很容易破坏域的隔离属性 ( unsafe 代码允许任意 的内存访问)。为了对 safe 和 unsafe 的边界进行清晰的划分，Moat 在域基础库中对低 级内核资源的不安全操作进行了封装和安全抽象，并为隔离域暴露出安全的接口。具 体而言，域基础库中对内存读写、设备 I/O、指针操作、寄存器访问、同步原语等低 级内核资源进行了安全抽象。
本文以 Linux 上的自旋锁安全封装为例，展示如何在 Rust 中封装一个更安全的 自旋锁。在 C 代码中，开发者使用 spin_lock_init 函数初始化自旋锁，然后使用 spin_lock 和 spin_unlock 函数来加锁和解锁。这意味着开发者需要手动管理自旋 锁的生命周期， 并确保在使用完毕后正确释放它们， 尽管直观来看这些操作是安全的， 但在实际开发中，开发者可能会忘记释放自旋锁，从而导致死锁或其他问题，这在一

些复杂的函数中尤其容易发生。
在Rust 侧， 尽管可以通过FFI 来调用这些接口， 但由 于这些接口是 C 语言的，因此需要将它们放置在 unsafe 代码块中，从而在代码库中 引入大量的 unsafe 代码。在 Rust 中，最好的做法通常是将资源的管理权交给编译器， 由编译器来自动管理资源的生命周期。为了实现这一点， Moat 使用 Rust 定义了一个 SpinLock 类型， 并在其安全构造函数new 中使用 spin_lock_init 初始化自旋锁， 并 根据初始化结果返回一个 Result<SpinLock,Error>，unsafe 代码块被隐藏在 new 方 法中。Result<SpinLock,Error> 类型比 C 语言的返回值要更符合语义， 因为C 代码中 仅仅使用负数表示错误值， 而这往往被调用者忽略， 相反，Result<SpinLock,Error> 类型强制调用者处理错误情况。SpinLock 拥有一个 lock 方法来加锁， 与C 不同，lock 方法将会返回一个 SpinLockGuard 类型的对象， 这个对象实现了 Drop trait ， 在作 用域结束时会自动调用 spin_unlock 来释放自旋锁，这是由 Rust 的所有权系统和生 命周期管理机制自动处理的。这样，开发者就不需要手动管理自旋锁的生命周期，避 免了忘记释放自旋锁导致的问题。
对于其它低级内核资源，域基础库也提供了类似的安全抽象。通过这些抽象，开 发者可以在隔离域中安全地使用这些资源， 而不需要直接处理unsafe 代码， 从而确保 隔离域的安全性和可靠性。

3.3.2 基础库的安全抽象

 尽管具体的实现会因为系统的差异而有所不同，但 Moat 为基础库的设计和实现 提供了一些通用的指导原则和类型抽象。
最小化原则 域基础库只会对最底层的低级内核资源和相关联的不安全操作进 行安全抽象，而可以由这些资源和安全接口组成的高级抽象和接口则是由域自行实 施，因为这些不再需要 unsafe rust。与 redleaf[45]中每个隔离域依赖不同的可信库相反， Moat 通过域基础库中的安全抽象为所有域提供了访问低级内核资源的统一途径，避 免了为大量外围设备驱动编写可信库的需要。而且， Moat 尽可能将更高级的抽象留 到域中实现，这在很大程度上减少了域基础库所包含的代码，从而降低了对其内部 unsafe 代码的审查难度。
内核资源的安全回收 所有需要手动分配和释放的资源都必须进行封装并实现 Rust 内置的 Drop 特性。这将内核资源管理从开发人员的手动操作转变为编译器驱动 的自动化操作。此外，在发生域故障时，故障处理流程也可以正确回收这些资源。通

过这种方式，Moat 在不破坏已有接口的情况下，确保了隔离域中的资源使用是安全 的。
域状态数据的安全存储 域使用域基础库中的安全抽象实现其功能，这意味者一 些内核资源可能构成域的状态数据。
对于绝大多数资源来说， 它们是平凡的数据结构， 因此不会进行堆分配。然而，少部分安全抽象内部可能会分配堆空间，默认情况下， 这些堆分配发生在域的私有堆上。在域将资源作为状态数据来看待的情况下，这些资 源就需要被分配到自定义堆当中，从而可以在域热更新后继续存在。为此，域基础库 为这些类型添加了一个额外的构造函数， 在这个额外的构造函数中堆分配被指定到域 的自定义堆上。
内存访问的安全抽象 域基础库将域可以访问的内存分为两类，类型化内存和无 类型内存， 两者可以互相转化。
域基础库定义了FrameTracker 来表示无类型的内存, 其对应到一段连续的物理地址区间。在系统中，无类型内存主要用于几个场景中： • 用于域的细粒度堆分配； • 用于与硬件交互，读取硬件数据或写入数据到硬件中； • 用于映射任务地址空间和访问用户数据。
类型化的内存包括域的代码、 数据段, 设备地址空间，Rust 堆。
在域被加载后， 无 类型内存自动转变为类型化内存，并由 Rust 的类型系统接管。例外之一是设备内存， 无法从无类型内存转变到 Rust 中的对应类型， 域基础库引入一个SafeIORegion 的类 型来表示设备内存，与其它类型的内存一样遵守 Rust 的所有权规则。在运行过程中， 域可以将 FrameTracker 动态地转换为具体的数据类型， 但是必须满足两个条件： （1） 无类型内存的地址需要符合数据类型的内存对齐规则； （2）: 无类型内存大小不能小 于数据类型的大小。
指针对象的安全抽象 在初始域集合被加载到内核后，一些驱动域从域管理运行 时获得设备信息，并接管硬件设备。通常，设备资源位于特定的内存地址区间，因此 对资源进行封装的数据结构需要一个指向其地址的指针，在 safe rust 中，域无法操作 裸指针，但却可以创建一个裸指针。为了防止域传递一个无效的裸指针，域基础库引 入了不可伪造对象，它将裸指针作为一个 64 位大小的 u64 基本类型看待，但被包装 在 SafePtr 类型下，这有点类似于类型别名，但在Rust 中 SafePtr 是一个与 u64 完

全不同的类型，SafePtr 的构造函数和大部分指针访问函数是 unsafe 的，这意味着域 无法在 safe 的代码中随意构造和使用这个对象， 但是域管理运行时可以构造， 域基础 库可以访问。在 Linux 系统中，不可伪造对象还被用于处理回调函数的重定向中 (§3. 7)，因为这些回调函数的参数大多由裸指针表示。

简单来说，运行时主要负责两部分功能： • 硬件管理：它初始化硬件、管理物理内存、处理特权级切换以及处理硬件中断 （与系统相关） 。
• 域生命周期控制：它将域加载到内核地址空间或从内核地址空间卸载，从而实 现隔离域的动态管理（与系统无关） 。
系统初始化 运行时与动态加载的域不同，在系统启动时，运行时就已经被加载

到内存中运行， 因此， 直观上来看， 运行时与传统的内核功能类似。在系统启动期间， 运行时会建立初始页表，在探测可用的物理内存后，运行时需要再次建立完整的页表 并对物理内存进行精细的管理。在完成基本所有的基本功能初始化后，运行时将会从 预先指定的内存中读取并加载一些基本的域， 这些域是整个系统实现正常运行所必须 的。比如一个基本的 PCI 驱动域用于扫描 PCI 总线以识别设备，一个块设备驱动域 用于读取磁盘，一个文件系统域用于访问磁盘上的文件，一个任务域用于创建进程。
在建立第一个用户程序后，运行时就会切换到用户态并开始运行第一个用户程序。此 后，运行时就陷入了等待中断或异常-进行中断异常的分发的循环当中。
域的管理 运行时还负责对域集合进行管理，在系统运行过程中，用户发出的域 相关的请求由运行时处理，主要的请求包含三类：
1. 加载域到内核地址空间；
2. 从内核地址空间中卸载域；
3. 动态更新已加载的域； 在处理加载域请求时，运行时使用 DomainLoader::load 将域加载到内核地址空 间，DomainLoader::load 实现了对域目标文件的解析以及重定位工作， 在将所有需要 加载的区域加载到内核地址空间后，运行时使用 storage 的 API 为域的状态存储创 建自定义堆，共享堆是所有域共享的，因此在启动时已经创建。在完成这些基本工作 后，运行时调用域的初始化接口，并在初始化接口中传递域自定义堆以及对共享堆的 引用。尽管域的私有堆分配是在域基础库中完成的，但其底层使用运行时管理的物理 页，这主要通过 DomainResource 接口来进行分配和释放，这些接口记录了分配元数 据。自定义堆和共享堆底层同样也需要物理页分配，但不需要经过 DomainResource 接口，因为它们不需要记录元数据。
域准备就绪后， DomainManager 会将其注册到内核中，以供其他域查询和使用。
比如，域可以使用 query_domain 接口获取其它域对象并调用其它域的功能，其参数 是域的唯一名称。域的卸载是加载的逆过程，运行时需要回收其分配的资源。对于热 更新， 它的处理类似卸载， 但与卸载不同的是， 域的自定义堆被保留， 因为状态数据需 要迁移到新的域中，storage::move_domain_storage 用于更新域的状态存储堆。如 图 3.1所示，为了和已有的系统兼容，Moat 的运行时还需要协调原有的模块和域之间

的调用关系。也就说，运行时需要将原来的直接函数调用转换成对域接口的调用。这 种转换是针对单个域实施的，无法使用一套相同的接口进行覆盖。

3.5.1 域间通信与隔离

 Moat 通过将域的实现限定在 Rust 的安全子集之内并提供域基础库以封装域所需 的 unsafe 操作来确保域获得了 Rust 语言提供的安全保证。然而，这还不足以实现完 全的内存隔离，因为域仍然可能通过域接口传递包含复杂层次和引用关系的对象。为 了解决这个问题，在之前的许多工作 [43,89]的基础上，Moat 引入私有堆和共享堆来满 足域自身所需的堆分配和域间通信所需的数据传递。
私有堆 域的内部需要进行堆内存分配，Moat 通过为每个域建立一个私有堆来隔 离域对堆内存的访问 (Figure 3.2)。
与C 语言的堆分配不同，Rust 的堆分配由一个全局 的堆分配器进行管理，而每个被独立编译的域都需要声明其堆分配器， Moat 将这个 分配器视作域的私有堆。域管理运行时管理域的功能之一是为域分配较大的页，并记 录页的域所属权。在域内部，这些页被全局堆分配器用来分配较小的对象。采用两级 分配器有助于域管理运行时在系统运行期间快速为域分配内存资源， 并且在对域进行 卸载或更新期间可以安全且快速地回收这些资源。
由于域只能从自己的私有堆上分配 对象，域不能存在指向其它域的私有堆的指针。
域接口限制 通常， 单个域可能并不能完成所有功能， 需要通过域接口访问其它域 的功能。为了阻止域接口成为私有堆对象的逃生通道， Moat 为所有域提供一个全局 共享堆，并规定域间通信的数据共享通过共享堆完成。然而，单靠共享堆并不能约束 域间传递数据的方式，比如，域可能将私有堆数据放置在共享堆 (Figure 3.2) 中进行 传递。为此，Moat 引入了特殊的共享堆基本数据类型 DBox<T>，并在此基本类型上 构建其它数据类型。DBox<T> 通过 Rust 的 auto trait 特性来实现（1） ：共享堆上分 配的对象不能包含指向私有堆的指针； （2） ：共享堆上分配的对象不能存储私有堆对 象。
此外，Moat 不允许域接口使用可变对象引用， 虽然可变对象方便对数据修改， 但 会使得实施域的故障隔离变得困难。相反， Moat 使用不可变引用共享数据或通过移 动共享堆对象所有权来实现对数据的修改。
DBox<T> 与 Rust 的内置类型 Box<T> 类似， 但引入了一个额外的字段来记录其所 属的域。在进行域间通信时，如果需要移动所有权，该字段会被更新为新的域标识符 并在调用完成后恢复。移动所有权意味着调用者失去访问权。在域被卸载或更新时， 域管理运行时扫描被分配的共享堆对象，回收所有权属于该域的共享堆对象。
直观来看，域间通信就是对域接口函数调用，这比那些需要进行特权级切换的方 式要更高效。从本文实现的原型系统和在 linux 上的应用来看，对域接口施加的安全 限制，并不会对域的功能开发产生额外的负担。
如何将已有的模块接口转换为域接口？尽管可以直接从零根据域接口定义实现一 个域，但从简化工作的角度来看，将一个实现完成的模块改造为一个域是一个更好的 选择。然而，由于隔离属性的限制，模块的接口不得不进行修改以满足其要求。这里 以一个简单的块设备模块为例，展示如何将已有模块改造为一个域。如代码 1和2所 示，改造前后的接口差异主要来自其参数上。在改造前，调用块设备驱动的模块直接 使用 data: &mut [u8] 读取磁盘数据，此时，这里的 data 所代表的内存仍然属于 调用者，但是块设备驱动也拥有修改的权限，同样，使用 data: &[u8] 将数据写入 磁盘也导致调用者的内存对块设备驱动模块可见，这和模块的内存隔离是相违背的， 也就说，作为被调用者，不应该拥有调用者的私有数据的访问权限，更不能拥有修改 其私有数据的权限。在改造后，调用块设备驱动域接口的模块不再直接传递私有数据 的可变引用或不可变引用， 而是直接移动共享堆数据的所有权或使用共享堆数据的不 可变引用。调用者在使用 data: DVec<u8> 读取磁盘时，data 的所有权被移动到块 设备域中， 此时其只能由块设备域访问， 这是由Rust 的类型系统保证的， 只有块设备 域正确读取了数据，才能将该数据的所有权返回给调用者。调用者仍然可以使用不可 变的 data: &DVec<u8> 写入磁盘数据而不违背隔离规则，因为此时 data 并不是域 的私有数据。

3.5.2 域的故障隔离

 鉴于操作系统的复杂性，消除所有错误是不现实的，但内核需要限制错误的影响 范围，防止发生故障的模块破坏其它模块。在 Moat 中，内核分解和域的内存隔离属 性促进了故障隔离的实施。分解意味着故障发生在较小的单个隔离域中，内存隔离属 性确保了发生故障的域不会擅自修改其它域的内存。
为了实现域的故障隔离，Moat 需 要解决的一个核心问题是: 如何正确处理故障？
Rust 语言使用 panic 来表达程序故障，根据编译时配置，程序可以选择在发生故 障时直接终止程序的执行 (abort) 或者对执行流进行堆栈展开 (unwind)。
为了捕获并处 理域的故障，Moat 依靠 Rust 语言内置的 panic 钩子和故障捕获点。在编译时， Moat 会修改域的编译选项以启用 unwind 策略，域管理运行时在域加载时将编译器产生的 DW ARF[90]信息一同加载。DW ARF是一种调试信息格式， 提供了关于机器代码如何映 射到源代码的信息，特别是用于跟踪栈帧的信息。
DW ARF中有一种称为 Call Frame Information（CFI） 的结构， 它记录了每个函数调用点的信息， 用于帮助编译器和调试 器知道如何展开栈。
在域内部，Moat 为每个域定义 panic 钩子， 当域中出现故障时， 执行流将会跳转到 panic 钩子中进入故障恢复流程。在钩子中，Moat 的展开器会沿着当前栈帧向上展开， 即从当前的栈帧逐步退回到调用方的栈帧。在每一个栈帧中，它会依次调用栈中每个 活跃对象的 Drop 方法，确保资源被释放。如果程序中有代码显式捕获了 panic，比 如通过使用 catch_unwind， 那么堆栈展开过程在捕获点停止， 程序可以在捕获panic 后执行特定的逻辑（如记录日志或恢复执行） 。如果没有捕获到panic，那么 unwind 过程最终会导致程序终止。为了将故障隔离在单个域中， Moat 将故障捕获点被定义 在域的入口处，也就是在调用域接口的位置，这确保 unwind 最终始终会在故障捕获 点处停下，结束故障处理。

一部分是它自己的CFI 指令， 一部分是链接到该函数所属的CIE（Common Information Entry ） ，其中包含公共规则与基础约定。展开器先加载 CIE 和 FDE，然 后执行它们所包含的 DW ARF CFI指令。这些指令不是机器码，而是描述性语言。展 开器会按指令逐条解释，构建出一个虚拟的“帧描述状态” ，这个状态告诉展开器：
CFA（Canonical Frame Address ）是什么、调用者的返回地址寄存器保存在什么位置、 调用者的 SP/RBP/其他寄存器如何恢复。
CFA 通常是“调用者栈帧顶部”的抽象地 址，DW ARF会用它作为参考基准，计算出返回地址位于 CFA-8，保存的旧帧指针在 CFA-16。
但编译器优化场景下， 这些寄存器可能放在任意寄存器或栈槽里， 或者只在 某段指令范围内有效，这些变化都通过 CFI 的指令流描述出来。
当展开器解释完当前 FDE 的 CFI 指令后，它就得到了完整的“上一帧寄存器状 态” 。首先， 根据返回地址规则， 它会从CFA+ 偏移处读取出返回地址（RA） ， 作为上 一层函数的下一条指令地址。然后根据规则恢复上一帧的 SP、BP 和所有被调用者保 存的寄存器。得到这些之后，展开器构造“上一帧的机器现场” ：新PC 地址、新栈指 针和其他寄存器。接着，它将这一帧视作新的“当前帧” ，再次根据返回地址去查找 对应的 FDE，然后重复上面同样的解释过程。这就是堆栈展开的迭代方式：利用 RA 找到上一函数的 FDE → 执行 CFI 指令 → 还原上一帧寄存器 → 再往上。
此外，在恢复栈帧之前，展开器会查找当前函数的“异常处理表” （LSDA） 。这 个 LSDA 也是由编译器生成的，与 DW ARF结构紧密关联：其中的“action table”告 诉展开器本帧是否包含需要在 panic 发生时调用的清理逻辑。Rust 语言就是通过这些 action entries 挂接自己的清理代码。如果该函数中有需要 drop 的变量，Rust 编译器会 保证此处生成一个 landing pad， 这个landing pad 不是正常的函数控制路径， 而是一个 清理入口， 用来执行生命周期中要求的drop。
在执行展开时， 检测到当前帧有cleanup action，就调用这个 landing pad。landing pad 内部再调用 Rust 的 drop 胶水代码：这是 编译器为特定类型自动生成的释放逻辑，例如 Drop trait。
通过为内核资源实现 Drop 特性，Moat 在堆栈展开期间自动释放这些资源，从而

防止故障处理后出现资源泄漏和死锁。这种异常处理方法在 C 语言中更具挑战性, 这 也使得 Moat 可以简化对不同资源的处理，从而避免像 SafeDriver[10]使用复杂的资源 操作记录来处理不同类型的资源。此外，得益于域的隔离边界，故障恢复很快在域入 口处结束而不需要对任务执行流执行完整的堆栈回溯 [44,91], 这减少了故障恢复花费的 时间。
执行流的堆栈展开不会影响域的服务， 其它位于域中的任务的执行流仍然正常进 行。但由于域出现了故障，有很大概率是域的实现出现了错误，为了表达这一特征， 在 panic 处理流程中，Moat 发出警告信息并记录域发生崩溃的次数。在用户态，Moat 暴露了一个 domainfs，向系统维护者展示系统中所有域信息，同时也包括域的故障 计数。维护者可以根据故障计数判断错误的严重程度并决定是否对域进行更新修复。
不过， 基于unwind 的故障处理不是万能的， 首先，Rust 的 panic 不能发现所有的 故障，比如，堆栈溢出将会被 MMU 发现并被操作系统结束任务，硬件错误也不会被 panic 所发现。
另一方面， 当故障发生在域修改了一些内部状态之后， 故障恢复将不能 撤销这些修改，这可能会导致域出现更多的故障，此外，故障恢复期间如果系统内存 不足将会导致故障恢复失败。这些问题已经超出了故障隔离的能力范围，因此，Moat 将责任推送给系统维护者。
故障隔离代理 Moat 依靠故障隔离代理来自动实施故障隔离从而向外部隐藏处理 细节。具体而言，故障隔离代理将真正的域对象进行封装，并且实现和域对象相同的 trait，这相当于对域接口调用进行了一次中转。在内部，故障隔离代理将域对象的所 有接口调用包装在如代码 3所示的 catch_unwind 函数中， 这个函数使用Rust 内置的 特殊方法使得编译器生成故障捕获点，也就是生成了 DW ARF信息。相比在接口调用 时保存任务寄存器信息，这种方法不会给域间通信带来较大的开销。在域正常工作期 间，这个函数包装不会对域接口调用带来额外的副作用，只有在域发生故障时，故障 恢复流程最终将暂停在该捕获点处并返回一个错误以表征域内发生了故障，这样，发 生故障的域就不会向上返回错误的数据。这对一些设备驱动域是有用的，这些设备可 能因为某些原因导致请求失败而需要重试。

3.6 隔离域的热更新

 在像 Linux 这样的内核中做动态升级是困难的，最重要的原因是内核状态数据的 复杂性，内核模块之间互相交织导致一个模块的状态可能被多个模块共享和修改。基 于语言机制的模块隔离促进了域的状态数据隔离，域之间通过接口访问功能，因此域 不会共享特殊的全局状态，每个域是独立的部分，它们的状态数据也是独立的。已有

的工作大多将隔离和热更新视作两个独立的问题进行解决，或者像 Theseus[44]另辟蹊 径以无状态模块设计解决热更新的问题。与这些工作不同， Moat 将热更新和隔离结 合起来一起考虑，这不仅可以大大简化热更新的实施，还不需要推翻现有的常见的有 状态模块实现方法。

3.6.1 状态保存和恢复

 热更新的核心在于确保域在升级前后拥有相同的正确的状态。
当深入地考察域更 新前后所发生的变化，本文发现，对一些域的更新实际上不需要状态数据的保存和恢 复，Moat 把这种域称为无状态域。这里的无状态指的是域内部的数据是无关紧要的， 不需要在热更新的时候考虑。对于其它的域， Moat 称为有状态域，有状态包含两层 含义： （1）这些域内部确实保存了需要在更新前后保持一致的状态数据，比如任务管 理、虚拟文件系统等； （2）这些域更新后可以从一个初始状态重新开始运行，但是这 些域可能会独占机器的硬件设备，比如底层设备驱动程序。
通过对有状态域的分析发现，域中分配的大多数数据都会很快被释放掉，但是对 于域运行至关重要的状态数据则通常不会马上释放， 并且很多时候都被保存在堆内存 或者全局变量中， 这些状态数据仅仅占据域数据的一小部分。Plugsched[15]正是利用了 这一点， 结合模块中特定API， 它将模块中的状态数据以类似“pop”的操作移出旧的 模块，然后以类似“push”的操作移入新的模块。然而，这种方法过于和模块 API 绑 定，通用性比较差。Moat 从另一个角度出发：
1. 既然模块的状态数据和普通数据不同，那么就直接在定义时区分两者的存储方 式；
2. 既然模块状态数据需要在模块的整个生命周期中存在，那么只需要将状态数据 保存在一个可以持续存在的地方即可。

在升级内核模块时， 较 大的服务暂停时间会影响系统提供的服务。
最理想的情况是在更新时保持服务而不中 断，而对无状态域的划分可以实现这一目标。域是无状态的，意味着域对外提供服务 并不依赖自身存储的数据，这意味着在进行无状态域升级时进行以下操作：
1. 旧域仍然向外提供服务，并不会在更新时立即从系统中移除；
2. 新域被加载到内核中，新的任务使用新域的服务；
3. 在旧域中活动的任务全部离开后，域管理运行时再卸载旧域，此后所有的服务 由新域提供。
无状态域的 RCU RCU[92]是一种同步机制。
它允许读者在不加锁的情况下读取共 享数据， 同时确保写者能够安全地更新数据， 而不会影响正在进行的读操作。Moat 使 用 Linux 内核中流行的 RCU 机制来完成无状态域的升级。简单来说，Moat 把无状态 域视为需要并发访问的数据，域的普通访问者作为读者 (图 3.5路径 °)，域的更新者 作为写者 (图 3.5路径¯） 。这样就可以把RCU 的优势完美应用到对无状态域的热更新 中。当新的域加载到内核中时，旧的读者可以继续使用旧域提供的功能，而新的读者 不用等待所有旧读者离开就可以直接使用新域提供的功能。域的更新者会使用 RCU 同步原语确保所有读者离开旧域，域管理运行时就可以安全删除旧域所有的资源。
与 Theseus 的无状态模块不同，其无状态模块对外表征并非一个独立的对象，因 此在更新期间需要重写模块之间的依赖关系。在 Moat 中，访问域对象是通过指针间 接进行的，从而可以实现更新对象时的原子性，因此可以直接使用 RCU 机制来避免 服务暂停。
有状态域 有状态域与无状态完全不同，其提供的服务依赖内部的状态数据，如 果在更新期间有其它任务位于旧域中，并在更新域的同时修改了域中的状态数据，就 会造成状态数据不一致，引发严重的错误。因此，有状态域的更新需要确保所有的任 务已经离开旧域并阻止新的任务进入旧域中才能安全地重新初始化新域。
为了检查所有任务是否位于模块中并进行升级，大多数补丁工具 (比如 kpatch[11]) 使用 Linux 的 stop_machine 接口来让 CPU 进入静止状态， 在状态静止期间， 特定的 CPU 执行用户定义的处理程序，其余的 CPU 停止工作。Plugsched[15]进一步使用任务

3.7 Moat 适配方法

 这里，本文以 Linux 操作系统适配 Moat 架构为例。图 3.6展示了 Moat 如何集成 到 Linux 内核中。Moat 不会破坏现有的 Linux 内核结构，而是添加一个新的内核模 块作为域管理运行时来为隔离模块提供服务，而域基础库则作为安全的抽象层，使用 Rust 的安全特性封装现有的内核资源抽象。
在这种情况下， 域管理运行时和域基础库 子模块中与系统无关的部分可以直接在 Linux 内核中重用。然后，开发人员可以使用 安全的 Rust 重写现有的内核模块，将其转换为隔离域或创建新的隔离域。这种集成 方法使 Moat 能够利用现有的内核结构，同时为内核模块引入健壮的隔离机制。
域基础库的移植 本文从系统无关和系统相关的部分来分析域基础库。作为一个 库，域基础库无需作为单独的 LKM 存在，相反，它被作为依赖库编译到隔离域的可 执行文件中。由于域基础库由一系列小型库组成，因此系统无关部分无需修改即可重 用，而系统相关部分可以利用现有的内核基础架构。例如， Linux 内核已经为内核资 源提供了足够的抽象，无需从头构建这些抽象。然而，由于 C 语言实现与 Rust 的类 型系统之间存在显著差异，需要使用 Rust 封装现有的 C 语言接口和数据结构。因此， 内核资源的安全抽象变成了内核模块导出的外部接口的封装（图 3.6） ，还可以直接 使用 Rust for Linux (RFL) 项目[84] 中已经实现的封装来简化这部分工作。
域管理运行时的移植 与域基础库不同，域管理运行时模块是一个需要随内核运 行的组件。因此，在现有系统中实现域管理运行时需要在内核源代码中添加代码。然

而，在 Linux 中实现域管理运行时时，可以将其作为一个新的内核模块添加，而无需 修改内核源代码 （图 3.6） 。
与域基础库类似， 域管理运行时中与系统无关的部分可以 直接重用。而与系统相关的部分则需要根据现有内核结构进行调整。在 Linux 中，域 管理运行时中与系统相关的部分无需重新实现，而是直接使用 Linux 内核中其他模块 提供的 API。例如，为了使用 DomainLoader 实际加载域，Moat 可以使用 Linux LKM 的模块加载接口来分配虚拟地址空间。
这种分解有两个关键优势。首先，它将隔离覆盖范围扩展到大多数内核模块。其 次，将隔离基础设施与模块实现解耦，可以实现不同系统的无缝重用——这对于实际 应用至关重要。

3.8 本章小节

 本章系统阐述了 Moat 内核模块隔离框架的设计方案。该框架的核心在于构建一 个基于 Rust 语言安全特性的可信计算基， 其由隔离域基础库和域管理运行时组成， 负 责安全地封装底层操作并提供隔离机制。内核功能则被实现为完全由安全 Rust 编写 的隔离域，通过明确定义的接口进行交互，从而实现了隔离机制与业务逻辑的解耦。
Moat 通过为每个域建立私有堆来实现内存隔离，并通过全局共享堆及严格的类 型限制来安全地实现域间通信。域基础库将不安全的内核资源操作封装为安全抽象， 而域管理运行时则负责域的加载、卸载和生命周期管理。基于此隔离架构， Moat 能 够利用 Rust 的异常处理机制实现故障隔离，将模块故障限制在域内。
框架的创新性尤为体现在将隔离属性作为实现高效热更新的基础。
通过引入自定 义堆来显式管理域状态，Moat 能够支持域的热更新。针对无状态域，采用 RCU 机制 实现服务不中断的更新；对于有状态域，则利用隔离边界实现快速任务检查和状态迁 移，显著减少了服务暂停时间。
本文还以 Linux 为例介绍了适配 Moat 的方法，得益于良好的分解，Moat 可以方 便地插入到现有系统中，这避免了对现有系统进行破坏性的更改，又可以逐步引入隔 离的机制。总之，本章详细描绘了 Moat 框架如何通过语言安全、架构解耦和精巧的 机制设计，系统地解决内核模块隔离、故障隔离和热更新的难题，为构建更安全、更 可靠、更易维护的操作系统内核提供了一个切实可行的设计方案

内核回调函数重定向 在 Linux 中，内核可加载模块的常用做法是通过向内核注 入回调函数来扩展内核的功能。模块可以使用内核导出的符号，向内核申请资源或者 释放资源。与 LKM 不同，域不能通过注册回调函数来扩展 kernel 的功能，因为 Moat 要求对域功能的访问全部从域接口进入。
为了让所有对域功能的访问通过域接口，需要禁止域注册回调函数。可以通过创 建中介函数来把内核回调函数重定向到域接口上来解决这个问题 , 这基于对内核回调 函数接口的观察结果上：这些回调函数参数指定的数据结构中，通常存在一个字段用 于保存实现者的私有数据。具体而言， Moat 按照内核回调函数接口定义来定义域的 接口，以尽可能减小两者的差异，在域初始化内核数据结构期间，域对象会被保存在

私有数据字段中， 在内核调用回调函数时， 首先调用定义的中介函数， 在中介函数中， 从私有字段中取出域对象，并调用域的接口，当这些数据结构被销毁时，从中释放域 对象。
内核编译 本文还修改了 Linux 内核的编译配置，实验中观察到在故障恢复期间 以及驱动初始化设备期间， 内核发生了崩溃， 其原因是任务内核栈发生了溢出。
通常， Linux kernel 为每个任务分配大小为 8k 的内核栈，这在绝大部分情况下是合理的。然 而，Rust 编译器尝试在栈上为堆变量分配空间，并在稍后拷贝到堆上，这导致内核 栈被快速地消耗掉。本文增大了内核分配给任务的内核栈大小来解决这个问题。当前 Rust 社区正在对编译器进行优化以减小 Rust 程序对栈空间的不必要消耗。

4.4 本章小结

 本章对 Moat 的实现进一步做了补充和描述，除了第三章设计方案中描述的内容， Moat 还实现了一系列辅助工具来简化用户开发。
首先， 隔离代理， 热更新代理等通常 实现域对象相同的接口，并且使用相同的内部逻辑，为了降低用户重复粘贴代码的负 担，Moat 利用 Rust 宏来自动生成模板代码。
其次， 域的开发有一套标准的流程，Moat 提供了一个自动化工具， 提供了交互式的接口让用户快速创建一个域模块的基本代码 结构，并处理其编译过程。
本章还介绍了 Moat 的两个案例， 一个是完全从零实现的AlienOS， 一个是将Moat 移植到 Linux 内核中并对 Linux 已有模块进行域改造。从零开发允许完全按照 Moat 的倡议和方法使用 Rust 实现一个功能完整的操作系统，从而验证基于语言机制实现 模块隔离和热更新的可行性。而 Linux 内核模块的改造则展示了 Moat 设计的通用性 以及适配 Moat 可能需要的更改。

对于任务状态同步来说，CPU 核心数量的增加意味着 IPI 数量的增加，从而增加 其花费时间。在实验中，本文观察到任务状态同步所增长的时间与 CPU 核心增长的 数量并非完全线性相关，产生这个的原因是一个微妙细节：如果 CPU 核心此时位于

用户态， 那它因为IPI 中断所花费的时间 (4-5us) 就比当前处于内核态中的 CPU(2-4us) 多，因为位于用户态的 CPU 核心在处理中断的过程中需要进行特权级切换并保存更 多上下文，而那些位于内核态的 CPU 也会根据是否处于 idle 状态而花费不同的时间。
为了近一步了解活跃工作负载对块设备驱动程序实时更新的影响， 本文在使能所 有 CPU 核心的条件下，逐步增加更多的任务读取该设备的数据。当扩展访问域的并 发任务数量时，会出现一个违反直觉的现象（图 5.7b） ：随着任务数量从1 增加到 32， 同步时间从 130 µ 秒减少到 64 µ 秒。出现这种反转的原因是，随着任务数量的增加， 因为工作负载的缘故，更多 CPU 核心将会有更大的概率处于内核态中，从而通过避 免特权级转换来降低 IPI 处理延迟，进而降低任务状态同步的时间。
虽然这些结果是在受控的实验条件下获得的，但实际部署在不同工作负载下，服 务停机时间始终保持在 100 到 200 μs 之间。这种稳定性归功于 Moat 的双阶段设计： 时间关键型操作（状态转移和替换）受确定性延迟约束，而成本可变的阶段（例如任 务状态同步）则通过统计优化动态适应系统状态。这种架构分离确保了即使在硬件扩 展挑战下也能实现可预测的最坏情况行为。

5.5 本章小结

 在本章中，本文评估了 Moat 的域隔离抽象开销，相较于同样使用语言机制实现 隔离的 Redleaf，Moat 大幅降低了跨域调用的开销， 隔离的Linux 驱动程序平均 I/O 吞 吐量仅下降 1% 到 2%。Moat 的故障恢复造成了少量空间开销，但相较于其带来的好 处，这是合理的。最后，本文评估了 Moat 的实时更新机制，与隔离机制的有效结合 使得实时更新具有良好的表达性和更短的服务暂停时间， 实时更新导致的服务停机时 间仅为 100 到 200 微秒。

结论

 本文介绍了 Moat，一种使用语言机制实现内核模块隔离和热升级的方法，用于 提高内核的安全性、可靠性和可扩展性。在 Rust 语言提供的安全保证基础上，基于 系统分解和模块化思想，Moat 提供了一个通用的用于实施模块隔离的框架，Moat 利 用私有堆和共享堆的设计来实现模块间的内存隔离和通信， Moat 还通过故障隔离加 强了内存隔离的有效性。在模块隔离的基础上， Moat 提供了对隔离模块的组件级热 更新支持，这依赖 Moat 提出的状态分离存储和高效的状态同步方法。本文通过实现 一个原型操作系统 Alien OS 来验证这个方法， 更重要的是， 本文将这个方法应用在现 代商用操作系统 Linux 上。
实验表明，Moat 是一个通用的架构， 其隔离具有很小的开 销，Linux 隔离驱动的 I/O 吞吐量平均仅下降 1%-2%，Moat 的组件级热升级导致的服 务暂停时间很短，在 100-200us 左右。未来，在已经实施的基础设施上，本文希望可 以为更多的 Linux 内核模块实施基于语言机制的隔离和热升级。
