## 第一部分：Linux 内核安全性与漏洞实例

### 背景说明
传统 Linux 宏内核因代码复杂性高、攻击面广而面临持续的安全威胁。以下三个真实 CVE 案例说明了这一点：

### 1. CVE-2022-0847 - Dirty Pipe（未初始化缓冲区标志）
- **漏洞编号**: CVE-2022-0847
- **影响版本**: Linux 5.8 - 5.16.x（以及 RHEL 8.x）
- **严重性**: CVSS 7.8（HIGH）
- **根本原因**: `copy_page_to_iter_pipe` 和 `push_pipe` 函数中，新建 pipe buffer 的 flags 成员未被正确初始化，导致包含旧值。
- **利用方式**: 非特权本地用户可利用此漏洞向只读文件背后的页缓存写入，进而提升权限。
- **引言适用点**:
  - 说明内核复杂性：一个看似局部的初始化遗漏，就能导致权限提升。
  - 论证攻击面问题：pipe 这类高频使用的内核组件容易被非特权用户触发。
  - 支撑"必须减少可被触达的内核路径"的论点。

**参考链接**:
- NVD 页面: https://nvd.nist.gov/vuln/detail/CVE-2022-0847
- Dirty Pipe 官方分析: https://dirtypipe.cm4all.com/

---

### 2. CVE-2021-22555 - netfilter/x_tables 堆越界写
- **漏洞编号**: CVE-2021-22555
- **影响版本**: Linux 2.6.19-rc1 及之后（长达数十年）；CVE 发布时间 2021 年 7 月
- **严重性**: CVSS 7.8（HIGH）；Google CNA 评分 8.3
- **根本原因**: `net/netfilter/x_tables.c` 中堆内存管理逻辑错误，导致越界写。
- **影响范围**: 允许本地攻击者提升权限或触发拒绝服务。
- **引言适用点**:
  - 说明内核长期复杂性：同一个子系统的漏洞存在时间跨越多个主版本。
  - 论证 bug 修复成本高：netfilter 作为网络模块，历经多次迭代仍无法避免堆管理错误。
  - 支撑"修改一个功能模块影响全局系统可靠性"的论点。

**参考链接**:
- NVD 页面: https://nvd.nist.gov/vuln/detail/CVE-2021-22555
- Google 安全研究: https://github.com/google/security-research/security/advisories/GHSA-xxx5-8mvq-3528

---

### 3. CVE-2019-5736 - runc 容器逃逸（文件描述符误用）
- **漏洞编号**: CVE-2019-5736
- **影响版本**: Docker 18.09.2 前；runc 1.0-rc6 及更早版本
- **严重性**: CVSS 8.6（HIGH）
- **根本原因**: runc 在处理 `/proc/self/exe` 时，文件描述符管理不当，允许容器内进程覆盖宿主 runc 二进制。
- **利用方式**: 容器内攻击者可获得宿主机 root 权限，完全逃逸容器隔离。
- **引言适用点**:
  - 说明用户态-内核态边界问题：即使在较为隔离的容器运行时中，边界管理仍易出错。
  - 论证"隔离不能完全依赖单一机制"：需要多层次、显式的隔离策略。
  - 支撑"vDSO 等快速路径必须慎重设计"的论点。

**参考链接**:
- NVD 页面: https://nvd.nist.gov/vuln/detail/CVE-2019-5736
- 官方分析: https://brauner.github.io/2019/02/12/privileged-containers.html

### Linux Kernel Self-Protection 文档
**来源**: https://www.kernel.org/doc/html/latest/security/self-protection.html

**核心观点**（与本论文相关）:
1. **严格内核内存权限**
   - 可执行代码和只读数据不可写（`CONFIG_STRICT_KERNEL_RWX`、`CONFIG_STRICT_MODULE_RWX`）
   - 函数指针和敏感变量应尽量只读化（使用 `const` 或 `__ro_after_init`）
   - 适用点：论证为何必须限制内核代码被修改的机会

2. **内核与用户态内存隔离**
   - 内核不能执行用户态内存
   - 内核访问用户态内存必须是显式且受限的（x86 SMEP/SMAP，ARM PXN/PAN）
   - 适用点：支撑"域隔离必须包括内存权限分离"的设计

3. **减少系统调用暴露面**
   - 限制可用的 syscall 数量（`seccomp`）
   - 限制权限用户加载模块、访问兼容性接口
   - 适用点：支撑"AsyncAlien 通过域分解来限制每个域的 syscall 可见性"

4. **概率防御（KASLR、信息泄露防护）**
   - 内核基地址、栈基地址、动态内存基地址随机化
   - 防止内核地址泄露到用户态
   - 适用点：说明即使采取防御措施，也难以完全消除攻击机会

### 3. Trap、Syscall、内存管理对比
**文件**: `docs/graduation/x86-64与riscv对比.md`

**核心内容**:
- **Trap 处理**:
  - RISC-V: 向量写到 stvec，通过 sepc/scause 判断 trap 类型
  - x86-64: 中断描述符表（IDT），CPU 自动压栈返回地址、标志位等
- **Syscall**:
  - RISC-V: a7 传编号，a0-a6 传参数，sret 返回
  - x86-64: RAX 传编号，RDI/RSI/RDX/R10/R8/R9 传参数，iretq 返回
- **上下文结构**:
  - RISC-V TrapContext: 32 个通用寄存器 + sstatus + sepc + 内核栈指针
  - x86-64 TrapFrame: 15 个通用寄存器 + vector + error_code + CPU 自动压栈的 RIP/CS/RFLAGS/RSP/SS
- **内存管理**:
  - RISC-V Sv39: 三级页表，39 位虚拟地址
  - x86-64: 四级页表（PML4/PDPT/PD/PT），48 位虚拟地址

**适用于**:
- 论文第 1 章（引言）中说明"x86-64 迁移难点"
- 论文第 3 章（系统设计）中"平台抽象策略"
- 论文第 4 章（x86-64 实现）中"中断与异常""任务切换与系统调用""虚拟内存"各小节
