# 第3章 系统架构与设计

本章聚焦于在保持已验证设计原则下，将系统运行时与平台差异分离的总体架构与关键设计要点。目标是描述一套可移植的、可验证的设计方案，使得高层运行时逻辑不需要感知底层处理器与引导差异，同时为高频路径优化（如vDSO）保留清晰的接口与安全约束。

3.1 Alien 原始设计（基于语言机制）

Alien 的核心设计目标，是借助 Rust 语言所提供的类型安全与内存安全能力，将内核中的复杂功能拆分为具有明确边界的隔离域，并将与低级硬件资源相关的不安全操作尽可能收敛到最小的可信范围之内。与传统单体内核将大量功能直接置于同一可信边界内的做法不同，Alien 将系统划分为负责基础支撑的可信计算基（TCB）与一组相互隔离的域，使域内逻辑可以主要采用安全代码实现，而将底层资源控制、地址空间管理与跨域协调等工作集中于受控的运行时与基础库中。这种分层方式不仅降低了安全风险，也为后续的模块化演进与故障隔离奠定了基础。

在实现结构上，Alien 强调将隔离基础设施与域实现解耦。运行时负责域的创建、装载、调度与治理，基础库则为域提供对内核资源的安全抽象，例如内存分配、共享资源访问与受控通信接口。域本身作为独立的功能单元，以独立地址空间和受限资源视图运行，其实现应尽量避免直接接触底层硬件与全局状态。这样的设计使得域的行为更容易被验证，也使不同域在共享运行时支持的前提下保有相对独立的故障边界。

Alien 的域生命周期围绕“注册—准备—装载—启动—运行—替换”展开。首先，域镜像在系统中完成注册并进入可管理状态；随后，运行时为其准备地址空间和必要资源，并完成镜像装载与初始参数注入；在启动阶段，域通过统一入口进入运行态，并在后续由运行时持续执行治理与监控。对于需要更新或替换的域，系统应支持在不破坏整体运行的情况下完成状态迁移与资源回收，使旧版本能够安全退出，新版本能够接续服务。该生命周期设计的关键要求是原子性、可回退性与资源一致性，即任何阶段的失败都不应将系统置于不可恢复的中间状态。

在域间交互方面，Alien 采用共享堆、代理调用与显式的资源封装机制来支撑通信与协作。共享堆为高频数据交换提供了低开销路径，但其使用必须与清晰的所有权和生命周期规则相配合，以避免跨域对象在回收与复用过程中产生悬垂引用或状态污染。代理调用则适用于需要更强隔离或更明确语义边界的场景，通过中间层对请求进行转发、检查与调度，从而减少域之间的直接耦合。对于有状态域，Alien 进一步通过状态数据分离与版本化更新策略，降低升级过程中对运行服务的影响，并为故障恢复提供更稳定的语义基础。


从设计意义上看，Alien 的原始方案并不是单纯追求功能拆分，而是试图在语言机制、运行时控制与隔离边界之间建立一套可验证的工程结构。它将 unsafe 代码限制在狭小范围内，并通过安全抽象向上层提供尽可能完整的能力接口；同时，它又通过域的分解与共享机制，在安全与性能之间保持平衡。后续关于跨架构迁移、设备接入与高频路径优化的设计，都建立在这一原始架构之上，因此有必要首先明确其域模型、生命周期与通信机制的基本原则。


3.2 将 Alien 移植到 x86_64

启动与早期初始化是架构移植的首要问题。在 x86_64 平台上，引导到长模式、早期段与页表配置以及内核数据段的初始化等步骤，对地址空间布局与早期资源分配提出了明确要求。移植设计应在抽象层面规定统一的启动信息视图，包含可用物理内存区、内核与域镜像的预留区、以及处理器核心列表等元数据，以便上层运行时在各平台上采用一致的早期分配与保留策略。同时，应在早期内存分配策略中为关键运行时机制（例如 vDSO 与域镜像）预留确定性区域，减少不同引导语义对上层布局的影响。

中断、Trap 与系统调用的适配是保证运行时语义一致性的关键。x86_64 平台的中断与系统调用入口在寄存器约定、异常向量与调用栈语义上与其它架构存在差异，因此移植工作应在抽象层对这些元素进行语义映射：定义一致的上下文保存约定、系统调用参数传递语义与陷入后分发策略，以便上层的系统调用分发逻辑在不同平台间保持不变。平台适配实现负责把本地硬件机制与这些抽象契约对接，从而在不改变上层逻辑的情况下维持行为一致性。

虚拟内存与 ABI 兼容性是用户态兼容与域加载的基础。移植设计应提供统一的 VSpace 抽象，描述虚拟地址空间的初始化布局、内核与域镜像的加载位置策略以及地址保护语义；同时，在进程或域创建时应注入必要的辅助向量以向用户态传达运行时环境信息（例如 vDSO 基址）。对于 ELF 加载与重定位，设计需保证符号解析与动态链接在抽象层上完成，从而减小因架构差异造成的用户态兼容问题。

设备发现与驱动接入的移植工作应聚焦于将平台特有的枚举结果规范化为统一的设备描述。x86_64 常见的发现机制（如 ACPI 与 PCI 枚举）在元信息表达上与其它平台不同，移植层应负责把这些原生结果映射为包含设备类别、地址范围、中断语义与能力描述的标准化条目。基于该设备表，上层可以按统一策略决定驱动域的加载时机、权限授予与代理化处理，从而实现跨平台驱动域的复用并降低平台特有逻辑在上层的暴露。

以上四方面的设计应在保持语义一致性的前提下尽量把平台差异限定在抽象层与适配实现中，使得上层的域管理、镜像装载与运行时治理能够复用统一逻辑，从而实现从 RISC-V 到 x86_64 的平滑迁移并降低维护成本。

3.3 引入 vDSO

为降低高频系统调用的延迟并保持域隔离语义，我们在系统中引入了 vDSO（虚拟动态共享对象）作为用户态的快路径实现。vDSO 的工程化实现将其分为两部分：面向用户的只读数据区（以下简称 vVAR）与可执行的快速路径代码。内核负责 vVAR 的写入与维护，并以受控的无锁版本更新策略保证读写一致性；用户态快路径仅对 vVAR 进行只读访问并在本地完成常见查询，从而避免频繁陷入内核带来的上下文切换开销。

在一致性设计上，我们采用了基于版本号的读验证模式：内核在更新 vVAR 时先将版本号置为不可用态、完成数据写入后将版本号恢复为可用并递增版本号；用户态读取时按“读版本号→读数据→再读版本号”的顺序进行验证。若两次读取的版本号不一致，用户态快路径将进行有限次重试或按策略回退到慢路径系统调用，以保证语义正确性与可观测的回退行为。该机制在读多写少的常见场景下实现了低延迟读取同时保留了强正确性保证。

在映射与权限管理方面，我们在进程或域创建阶段将 vDSO/vVAR 映射到目标地址空间，并通过辅助向量向用户态传递 vDSO 基址信息，用户态运行时优先解析并绑定快路径函数符号。为确保安全性，映射策略限定 vVAR 为用户态可读、不可写，并由内核保持对写入与更新的独占控制；可执行快路径代码也被限制为不可直接修改内核状态，任何需要更高权限的操作均通过慢路径或受控代理完成。

为保证在异常或不一致场景下的健壮性，我们为用户态解析与调用设计了明确的回退策略：当用户态解析失败、验证不通过或检测到运行时异常时，调用路径会透明地回退到系统调用实现，以保证功能正确性。通过在若干典型场景中对比快路径与慢路径的行为，我们在实验验证中观察到 vDSO 在延迟与抖动方面的显著改进，同时在并发更新情形下保持了可预测的回退正确性。
